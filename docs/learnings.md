# Text Refiner — Build Learnings

Notes from building a system-wide text refinement daemon on macOS. Short list,
written in plain language so the next person picking this up (or porting it to
another OS) doesn't repeat the dead ends.

## The shape of the problem

A "select text → trigger shortcut → AI rewrites in place" tool has three
distinct concerns. Each has its own correct toolchain.

1. **System integration** — global hotkey, reading the user's selection,
   replacing the selection in the foreground app.
2. **UI overlay** — a small picker on top of any app, including fullscreen.
3. **LLM call** — talk to Anthropic / OpenAI / etc., apply a system prompt,
   return text.

Mixing these in one language was the original mistake. The right split:

| Concern | Best tool | Why |
| --- | --- | --- |
| System integration | Native Swift / AppKit | TCC permissions, Accessibility API, NSPanel, CGEvent all live here |
| UI overlay | Native Swift / AppKit | Fullscreen Spaces, vibrancy, panel collection behavior need native APIs |
| LLM call | Python | First-class SDKs, easy iteration on prompts, simple subprocess interface |

## What worked

- **Native Swift daemon** for the actual app. The picker, hotkey, and selection
  handling all need native macOS APIs and TCC entitlements. Trying to do this
  in Python was where the first version stalled.
- **Python helper called as a subprocess.** The Swift app shells out to a
  tiny Python CLI (`refiner_cli.py`) that owns prompts and the Anthropic call.
  JSON on stdin and stdout. Easy to evolve prompts without recompiling Swift.
- **Accessibility API for selection read/write.** Where it works (native
  Cocoa apps: Notes, TextEdit, Mail, Safari fields, Slack) it is the cleanest
  path. No clipboard, no synthesized keystrokes, instant replacement via
  `kAXSelectedText`.
- **`NSPanel` with `.nonactivatingPanel` style** for the picker. Combined
  with `NSWindow.Level.screenSaver` and `.canJoinAllSpaces` /
  `.fullScreenAuxiliary` collection behavior, it appears over fullscreen apps
  on the current Space.
- **Subclassing `NSPanel` so `canBecomeKey` returns `true`.** Without this,
  the borderless panel never receives keyboard events and digit shortcuts
  pass through to the app behind it.
- **launchd LaunchAgent** for autorun and respawn. The plist template is
  generated by `setup.sh` so it gets the user's actual paths, never committed
  with hard-coded values.
- **`codesign --identifier com.textrefiner.native`** giving the binary a
  stable code identifier. Without this, every rebuild looks like a new app
  to TCC and the user has to re-grant Accessibility and Input Monitoring
  every time.
- **`NSVisualEffectView` with `.hudWindow` material** for the picker
  background. It picks up the user's Light/Dark mode automatically and feels
  like a native overlay.

## What didn't work

- **Tkinter** for the picker UI. It opened in its own macOS Space when
  triggered from a fullscreen app instead of overlaying on the current one,
  and forcing it to behave native took more code than just writing AppKit.
- **`osascript` / System Events for synthesizing `⌘V`.** Always failed with
  "not allowed to send keystrokes" on macOS Sequoia. TCC doesn't grant a
  background process the right to drive System Events as an Apple Event
  client without a separate Automation grant per-target app.
- **`CGEvent.postToPid(pid)` for delivering `⌘C` / `⌘V`.** Sent the event
  to the Electron host process pid, which is not where the keyboard handler
  lives in apps like Cursor, VS Code, Chrome. Global post is the right
  default; per-pid post was a wrong turn.
- **Setting only a modifier flag on a single key event for `⌘C`.** The OS
  combines synthesized events with the *current* hardware modifier state.
  When the user just released Right Option to trigger the app, that release
  hadn't fully propagated, so our `⌘C` arrived as `⌘⌥C` and copied nothing.
- **`NSEvent.addGlobalMonitorForEvents` as the only event listener.** Useful
  as a backup, but not enough on its own when you need to consume or reason
  about modifier state precisely. A `CGEventTap` is the right primary source.
- **Embedding the API key in the LaunchAgent plist.** Was the first thing the
  original repo did. Replaced with `keyring.get_password("text-refiner",
  "api_key")` so the secret lives in the macOS Keychain.

## When to reach for Python vs Swift

- **Python for**: anything that calls an SDK (Anthropic, OpenAI, Gemini),
  prompt template management, text formatting, data manipulation, history.
  Use it as a subprocess that takes JSON on stdin and returns JSON on stdout.
- **Swift for**: anything touching macOS APIs — global shortcuts, event
  taps, NSPanel/NSWindow, Accessibility API, launchd integration, code
  signing, TCC-permission-bearing operations.

Rule of thumb: if the docs are on developer.apple.com, write it in Swift.
If the docs are on the model vendor's site, write it in Python.

## macOS permission gotchas

- **Stable code identifier or pain.** `codesign --force --sign - --identifier
  <reverse-dns>` after every build. TCC binds permissions to the identifier
  for ad-hoc-signed binaries, so without it every rebuild silently revokes
  permissions and the user gets confusing "no" results from the API.
- **A binary appearing in the Accessibility list with the toggle ON does not
  mean it's trusted.** After certain rebuild patterns (including `pkill` +
  relaunch via launchctl) the UI says ON but `AXIsProcessTrusted()` returns
  false. Fix: toggle the permission OFF then ON again. We now log
  `AXIsProcessTrusted` at startup so this is visible.
- **`Cmd+C` synthesis is silently dropped if Accessibility isn't trusted.**
  The pasteboard's `changeCount` won't bump. Always gate the workflow on a
  changeCount increment; never trust the clipboard's existing content as if
  it came from your own synthesized copy.
- **Electron apps (Cursor, VS Code, Chrome) usually don't expose
  `kAXSelectedText`** on the focused element, even when other Cocoa apps do.
  Your fallback path (synthesized `⌘C` / `⌘V` plus clipboard) is the only
  thing that works there.
- **Right Option as a trigger key** needs the OS to fully register the key
  release before you synthesize the next shortcut, or your modifier flags
  leak into the new event. A ~80–180 ms delay between detecting the gesture
  and synthesizing is the difference between "works" and "silently fails".

## Architecture in one breath

```
launchd ──► TextRefinerNative (Swift)
              │
              │  - CGEventTap for double-tap Right Option
              │  - NSPanel picker over fullscreen Spaces
              │  - AXUIElement read / write for selection
              │  - Clipboard + synthesized ⌘V fallback
              │
              └──► refiner_cli.py (Python, subprocess)
                     │
                     │  - load mode prompt
                     │  - call Anthropic SDK
                     │  - save history
                     │
                     └──► returns JSON {ok, text|error}
```

Three boundaries. Each owns one thing. Each can be replaced independently.
